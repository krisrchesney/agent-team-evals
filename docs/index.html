Do teams of AI agents write better code than one agent?

Agent Team Evals runs Claude Code on coding tasks with hidden tests, alone and in teams, and measures two things: how often each setup passes, and how many tokens it uses to get there.

Read the write-up Code and raw results on GitHub Design notes

So far, adding a reviewer hasn't clearly made one agent better. Two studies have run Claude Code alone and in teams. In the first, on tasks with their rules written down, one agent passed 38 of 39 runs, which left a team little to fix. The second used tasks picked because one agent can fail them, mostly with unwritten rules or decisions only a person can make. There, one agent passed 15 of 55 runs and a builder plus reviewer passed 11 of 55 at 1.5x the tokens. That gap is within chance, so this doesn't show that teams are worse, only that they showed no gain. Changing models didn't help either: no other model or mixed team beat one Sonnet agent. Every setup here runs agents one after another, so parallel work is still untested, and so are repos too big for one agent's context.

The setups

The project started with three setups. Each gets the same model, tools, turn limit and budget, so only the team structure differs. Later sections add a few variations and try other models.

A

Single agent

One agent reads the task, writes the code and runs the visible tests.

solve
B

Builder + reviewer

A builder writes the code; a read-only reviewer checks it against the request. If it asks for changes, the builder gets one fix round.

build → review → fix?
C

Planner + builders + reviewer

A read-only planner splits the work into subtasks, builders do them in turn, then the same review and fix round as B.

plan → build × n → review → fix?

What gets tested

Each task is a small, made-up Python codebase plus a request, written the way a colleague might ask for a change. The agent edits the code, and then hidden tests it never saw grade the result. A run passes only if every hidden test passes, so one missed rule fails the whole run. A reference solution proves each task can be solved.

One task up close: repeating appointments

The request names the new operations and says the practice manager can be asked about open decisions. It doesn't say what a monthly appointment on the 31st does in a shorter month, or what happens when one date clashes with an existing booking. An agent can ask a stand-in manager, which answers from a hidden sheet: the appointment moves to the month's last day, and a clashing date is skipped while the others still get booked. Hidden tests check each of those rules, so an agent that guesses differently can write tidy, working code and still fail.

Under-specified tasks

When every rule is written in the prompt, a careful agent can check its own work and a reviewer has nothing to add. The last tasks in this study read like a real request from a colleague instead:

t19 · Refunds

"Add refunds to the payments service; the API is in docs/API.md." The ledger entries, audit log, events, idempotency and error codes are only in the service's conventions and docs.

t20 · New supplier

"Load Corvid's invoice files like the other suppliers." Payment terms, default currency, cancelled lines and error handling live in the importer contract and config.

t21 · Statement bugs

Two customer complaints, symptoms only. Four root causes in shared code; the statement docs define "correct" for every customer.

Rules that are written down somewhere in a small repo are not hidden enough: the next test needs rules that are only implied by the code, a much larger codebase, or a request where the agent has to ask.

Second study: 235 runs on tasks one agent can fail

A team needs failures to fix, so the second study went looking for them. Twenty-eight new tasks (t22–t49) went through a screen of two single-agent runs each. A single agent passed both runs on 13 of them, and 4 more were dropped because their tests were debatable. That left 11 tasks. Each setup ran 5 times per task on Sonnet 5.5 (2026-11-01). Of the 11, two have rules implied by code, two are long specs, and seven have open decisions. Sweeps and per-task tables are in the full report.

  • A Sonnet reviewer didn't rescue a Haiku builder. It approved 31 of 33 runs, and 27 of those failed. Neither run it flagged passed.

On the last four tasks, Opus covered 83% of decisions and Haiku 65%.
  • Tokens are a poor guide to plan usage across models. Opus's 5.4M tokens moved the 5-hour bar about 27 points, and Haiku's 12.6M about 2. Other sessions may have added to both.

The extra agents read the same request as the first one, so a rule nobody wrote down is as invisible to them. The reviewer asked for changes in 9 of 55 team runs in the second study and all 9 still failed. In the first study it asked 4 times in 30 runs and all 4 became passes, so review can catch mistakes in work that a request fully describes.

Next are ten more tasks where the agent has to ask, already written and being screened, and then a test of parallel work.

How it runs

  • Each run is headless Claude Code in its own git worktree, with a clean profile: no connectors, plugins or memory leak in.
  • The harness, not the model, runs the stages in a fixed order, so the setups differ only in structure.
  • Hidden tests are copied in only after every stage has finished. Results are one JSON line per run, with tokens split into input, cache reads, cache writes and output.
  • Runs use a Claude subscription. Usage is reported in tokens, turns and time; caps exist to stop runaway loops.

Caveats

  • Small samples: the pilot is 5 tasks × 3 runs per setup, and differences under about 15 points of pass rate are not detectable at that size. The second study has 11 tasks; an earlier simulation wanted about 20 to detect a 20-point gap.
  • The second study's tasks were picked using Sonnet to make one agent fail, so its pass rates describe those tasks, not typical work, and the choice may tilt the comparison toward Sonnet. Repeated runs of a task are not independent evidence about other tasks.
  • Some hidden tests are debatable and partly a flaw in the tasks. They stay in place because real results exist, and the second score above is one reviewer's judgement.
  • One model family, tasks written for this project, and teams orchestrated in a fixed order rather than by the model.
  • Probes are one run per task: they show whether a single agent can fail, not how often.
