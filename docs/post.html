Do agent teams beat a single agent?

Kristopher Chesney · October 2026 · Project overview · Code and raw results

Not on anything I tested. Across 21 coding tasks, one Claude Code agent passed the hidden tests as often as a team of agents, within the noise of a small sample, and used a fraction of the tokens. The team's extra reviewing and planning had almost nothing left to fix.

The setup

Each task is a small Python repo, a written request, and a set of hidden tests the agent never sees. A run passes only if every hidden test passes. I compared three setups, all on Claude Sonnet 5.5:

  • A: one headless Claude Code agent.
  • B: a builder, then a read-only reviewer, then one round of fixes if the reviewer asks for any.
  • C: a planner, then one or more builders, then a reviewer and one fix round.

Every run starts in a fresh git worktree outside the project, through a Claude Code profile that holds only a login: no connectors, plugins, memory or personal instructions. The harness records pass or fail, tokens (input, output, cache reads and writes, summed over every stage), turns and wall-clock time. Everything ran on a Claude Max subscription, so the token counts are what I measure; nothing was billed per token.

The single failure was config A on a CSV report task: it printed 0 where the spec asked for 0.00. One failure in 15 runs is well inside the noise; the 95% intervals for the three pass rates overlap almost completely. The usage gap is large and consistent: B used 1.6 times A's tokens and C used 2.8 times.

The reviewer did catch real defects. It asked for changes in 4 of the 30 B and C runs, and the fix round turned all four into passes; one of them was the same 0.00 bug that sank A. The planner mostly had nothing to plan: in 12 of 15 C runs it produced a single subtask, so C paid for a planning stage and got one builder anyway.

Trying to make one agent fail

A team can only help where a single agent fails, so I kept writing harder tasks and ran config A once on each:

  • Nine larger tasks (t06 to t14): 9 of 9 passed, 854,488 tokens in total.
  • Four long specs (t15 to t18), 25 to 36 numbered requirements and 88 to 134 hidden tests each, one of them a hunt for seven planted bugs: 4 of 4 passed, 1,035,437 tokens.
  • A weaker model: Claude Haiku 5.5 on t15 to t18 plus t12 passed 5 of 5. On t15 to t18 it used 3,073,469 tokens, about three times what Sonnet used, and still needed no reviewer.
  • Three under-specified tasks (t19 to t21): a short, realistic request where the rules live in the repo's own conventions doc, config and code. Add a refund operation the way the others are built; import a new supplier's file format; fix two customer complaints with four root causes between them. 3 of 3 passed, 318,037 tokens.

Counting the smoke and calibration runs, a single agent has now done 39 real runs. It failed once.

What this shows, and what it doesn't

On small repos where the rules are written down somewhere, a single current agent rarely misses, so a reviewer and a planner mostly add tokens and time. If you pay per token, config A cost about 76k tokens per passed run against B's 114k and C's 197k (API-equivalent estimates: $0.066, $0.103 and $0.181).

The pilot has five tasks and three runs per cell, so differences under about 15 points of pass rate are invisible at this size. Every task was written by me for this project and fits in a small repo. The teams run in a fixed order set by the harness, not orchestrated by the model. Everything ran on one model family. So this data says teams added little on these tasks, and nothing about where they might help.

What would change the answer

A team needs failures to fix. The tasks most likely to produce them are ones I haven't built: rules that are only implied by existing code, repos far larger than one context window, and requests where the right move is to ask a question first. A fair test would also give the single agent the same budget, for example the best of two independent attempts, so any team win reflects structure rather than extra compute. If a single agent starts failing on tasks like those, the reviewer's 4-for-4 record in the pilot says it is the first thing worth adding back.
