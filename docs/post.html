Do agent teams beat a single agent?

Kristopher Chesney · October 2026, updated November 2026 · Project overview · Code and raw results

Not on anything I've tested so far. On the first 21 coding tasks, one Claude Code agent passed the hidden tests as often as a team of agents, within the noise of a small sample, and used a fraction of the tokens. So I wrote harder tasks that a single agent can fail, and the teams still didn't pull ahead. That covers review teams working one after another on repos up to about 3,000 lines. I haven't tested parallel work or much larger codebases.

The setup

Each task is a small Python repo, a written request, and a set of hidden tests the agent never sees. A run passes only if every hidden test passes. I compared three setups, all on Claude Sonnet 5.5:

  • A: one headless Claude Code agent.
  • B: a builder, then a read-only reviewer, then one round of fixes if the reviewer asks for any.
  • C: a planner, then one or more builders, then a reviewer and one fix round.

Every run starts in a fresh git worktree outside the project, through a Claude Code profile that holds only a login: no connectors, plugins, memory or personal instructions. The harness records pass or fail, tokens (input, output, cache reads and writes, summed over every stage), turns and wall-clock time. Everything ran on a Claude Max subscription, so the token counts are what I measure; nothing was billed per token.

The single failure was config A on a CSV report task: it printed 0 where the spec asked for 0.00. One failure in 15 runs is well inside the noise; the 95% intervals for the three pass rates overlap almost completely. The usage gap is large and consistent: B used 1.6 times A's tokens and C used 2.8 times.

The reviewer did catch real defects. It asked for changes in 4 of the 30 B and C runs, and the fix round turned all four into passes; one of them was the same 0.00 bug that sank A. The planner mostly had nothing to plan: in 12 of 15 C runs it produced a single subtask, so C paid for a planning stage and got one builder anyway.

Trying to make one agent fail

A team can only help where a single agent fails, so I kept writing harder tasks and ran config A once on each:

  • Nine larger tasks (t06 to t14): 9 of 9 passed, 854,488 tokens in total.
  • Four long specs (t15 to t18), 25 to 36 numbered requirements and 88 to 134 hidden tests each, one of them a hunt for seven planted bugs: 4 of 4 passed, 1,035,437 tokens.
  • A weaker model: Claude Haiku 5.5 on t15 to t18 plus t12 passed 5 of 5. On t15 to t18 it used 3,073,469 tokens, about three times what Sonnet used, and still needed no reviewer.
  • Three under-specified tasks (t19 to t21): a short, realistic request where the rules live in the repo's own conventions doc, config and code. Add a refund operation the way the others are built; import a new supplier's file format; fix two customer complaints with four root causes between them. 3 of 3 passed, 318,037 tokens.

Counting the smoke and calibration runs, a single agent has now done 39 real runs. It failed once.

Update: tasks a single agent can fail

A team needs failures to fix, so the second study went after them. I wrote 28 more tasks, with rules only implied by existing code, changes across about 3,000 lines and 60 files, long multi-step specs, and requests where the agent has to ask about product decisions. Each got two single-agent runs. A single agent passed both on 13 tasks, including all four of the larger repos. I dropped 4 more because their tests were debatable, which left 11.

Then every setup ran five times per task on Sonnet 5.5. Alongside A and B, seven tasks also got D (a fix round if the visible tests fail) and A2 (a second attempt if they fail). All 11 got AS, where a fresh agent re-reads the request and fixes what it finds.

Those gaps can't be told apart from chance, so I can't say the extra agents hurt. I can say that they used about 1.5 to 1.6 times the tokens and showed no gain. On the seven tasks that also ran D and A2, those two scored 8 and 10 of 35 against A's 10, but neither ever acted, because the visible tests always passed.

The reviewer approved 46 of 55 runs, and 35 of those failed the hidden tests. It flagged the other 9, and all 9 still failed after the fix round. Most failures were rules that the request and visible tests never stated, and a second agent reading the same request has nothing to check them against.

The decision tasks show one possible way in. On four tasks with a stand-in user to ask, all 11 runs that covered every decision passed, and one of the other 49 did. All 11 were on a single task, where the split was 11 of 11 against 1 of 4, so this needs more tasks before it means much. The extra agents barely changed the asking: coverage moved from 3.50 of 5 decisions to 3.60 and 3.65.

Part of the low pass rates is my own doing. Some hidden tests turned out to be debatable, including ones that fail on a reasonable reading of the repo. Dropping them, a judgement I made after seeing the results, lifts the first seven tasks to 22 of 35 for A, 16 for AS and 17 for B, and no setup moves ahead of A except A2, which behaved the same as A. Six of the 11 tasks failed in every run of every setup, so they couldn't separate anything.

What this shows, and what it doesn't

Where the rules are written down, a single current agent rarely misses, so a reviewer and a planner mostly add tokens and time. If you pay per token, in the pilot config A cost about 76k tokens per passed run against B's 114k and C's 197k (API-equivalent estimates: $0.066, $0.103 and $0.181). Where the rules aren't written down, one agent fails much more often, and a second agent reading the same words didn't recover them. Today I'd start with one agent, put the open decisions in the request or let the agent ask, and add a reviewer when the work can be checked against something the builder didn't have.

That last part is my inference, and these studies didn't test it. Neither did they test the setups people most often reach for: agents working in parallel on separate pieces, codebases too big for one context, or teams the model organizes itself. The harness runs agents one after another in a fixed order. The second study has 11 tasks where a simulation wanted about 20, all written for this project and picked to make an agent fail. Everything in it so far ran on Sonnet 5.5.

What comes next

Next is a run across Haiku 5.5 and Opus 5.5, including a cheap builder with a stronger reviewer, and then more tasks where the agent has to ask. A fair test of parallel work needs its own tasks and has to measure time as well as passes.
